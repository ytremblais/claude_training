Ce que cette formation couvre déjà
Les modules 6, 7 et 8 traitent la rédaction d'un prompt robuste, le partage en équipe et l'intégration dans le flux de travail — points également abordés dans la documentation Anthropic. Les concepts ci-dessous sont complémentaires et ne figurent pas dans les modules.
Concepts complémentaires à connaître
1
Concision et budget tokens
Le contexte est une ressource partagée. Anthropic recommande de garder le corps du fichier SKILL.md sous 500 lignes et de déporter les contenus longs (API, exemples, données de référence) dans des fichiers séparés chargés à la demande. Claude ne les lit que lorsqu'ils deviennent pertinents — zéro coût en tokens jusqu'à ce moment-là.
2
Degrés de liberté selon la fragilité de la tâche
La documentation distingue trois niveaux selon le risque d'erreur :
Haute liberté → instructions textuelles générales (plusieurs approches valides)
Liberté moyenne → pseudo-code ou scripts paramétrés (préférence sans rigidité)
Faible liberté → script exact à exécuter tel quel (opération fragile, séquence critique)
Analogie : pont étroit avec falaises = instructions précises ; champ ouvert = direction générale.
3
Tester avec tous les modèles cibles
Une Skill efficace sur Claude Opus peut être insuffisante sur Haiku (qui a besoin de plus de contexte) et sur-explicative sur Opus (qui sait déjà). Tester systématiquement avec chaque modèle prévu en production avant de déployer.
4
Convention de nommage des Skills
Anthropic recommande la forme gérondive pour les noms de Skills : analyzing-spreadsheets, processing-pdfs, generating-reports.
Règles techniques : minuscules, chiffres et tirets uniquement · max 64 caractères · pas de mots réservés (anthropic, claude) · pas de balises XML.
Éviter les noms vagues : helper, utils, data.
5
Description à la 3e personne (mécanisme de découverte)
La description est injectée dans le system prompt de Claude. Elle doit décrire ce que fait la Skill et quand l'utiliser, toujours à la 3e personne.
✓ "Analyzes Excel spreadsheets and generates pivot reports. Use when working with .xlsx files."
✗ "Je peux vous aider à analyser vos fichiers Excel."
Une description vague ("Helps with documents") empêche Claude de sélectionner la bonne Skill parmi 100+ disponibles.
6
Boucles de validation (feedback loops)
Pour les opérations critiques ou en lot (remplir un formulaire, migrer des données, modifier en masse), prévoir un cycle faire → valider → corriger → répéter. Exemple : générer un plan JSON → le valider avec un script → appliquer les changements → vérifier le résultat. Ce pattern intercepte les erreurs avant qu'elles ne se propagent.
7
Développement itératif avec Claude A/B
La documentation recommande un double rôle :
Claude A (expert) → aide à rédiger et améliorer la Skill
Claude B (agent) → instance fraîche qui utilise la Skill sur de vraies tâches
Observer comment Claude B navigue dans la Skill révèle les angles morts que l'auteur ne voit pas. Répéter le cycle observer → affiner → tester jusqu'à stabilisation.
Checklist officielle avant de partager une Skill
Qualité du contenu
  • La description précise ce que fait la Skill ET quand l'invoquer
  • Le corps de SKILL.md fait moins de 500 lignes
  • Les détails longs sont dans des fichiers séparés référencés à un seul niveau de profondeur
  • Aucune information périmable (dates, versions) dans les instructions principales
  • Terminologie cohérente dans tout le fichier (un seul terme par concept)
  • Les exemples sont concrets, pas abstraits
Tests
  • Au moins 3 scénarios de test rédigés avant d'itérer sur la Skill
  • Testée sur Haiku, Sonnet et Opus si ces modèles sont utilisés en production
  • Testée sur des fichiers réels, pas uniquement le fichier de conception
  • Feedback d'au moins un collègue intégré
